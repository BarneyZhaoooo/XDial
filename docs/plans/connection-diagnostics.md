# 连接自检与诊断改进计划（Apple 移动端）

2026-11-18 起草。范围：iOS / iPadOS（与 tvOS 共用 `appletv/XDialTV/TunnelManager.swift`、
`AppState.swift` 和 `appletv/XDialTVTunnel/PacketTunnelProvider.swift`）。macOS 走另一套
带任务报告的连接事务（`ConnectionTransaction`），没有这张“线路自检”卡片，本计划只在第 6 节单列。

现场反馈：iOS 已连接 0:10、有上下行流量，首页黄卡“已连接，但线路自检没通过 / 正在重新
检测线路…”，自动模式“在国内”；另有用户自检时有时无、连接很久。这些现象**不能**证明隧道
真的可用，也不能证明只是误报；下面的根因只是待验证的假设。

## 1. 现状：一次连接的关键路径

| 阶段 | 位置 | 时限 | 说明 |
|---|---|---|---|
| 保存、校验配置 | `AppState.performConnectionStart` | 无 | 同步 |
| 生成启动包并 `startTunnel` | `TunnelManager.startTunnel` | 启动看门狗 45 s | 后台队列生成配置 |
| 扩展启动 | `PacketTunnelProvider.startTunnel` | — | `start_begin → start_bundle_loaded → underlay_interface_ready → remote_address_resolving/resolved → network_settings_applied → tun_ready → engine_starting → (dns_settings_applying) → engine_started`；只持久化**最后一个**阶段 |
| 系统报告 connected | `applyConnectionStatus` | — | 此时首页**仍显示“检查中”** |
| 自检（首次） | `verifyDataPath` → `probeConfiguredDataPath` | 看门狗 90 s | 首页要等它结束才显示“已连接” |
| ├ Tailscale 就绪 | `waitForActiveTailscaleReadiness` | 登录等待不计时 | |
| ├ 线路试拨 | 每条目标线路 `probe-outbound-address` | 扩展 10 s / App 15 s | 并发；每条线路**依次**试 `checkip.amazonaws.com`、`1.1.1.1`，二者共用同一个 10 s |
| ├ 路由计数（前） | `routing-probe-snapshot` | — | |
| ├ 三个 HTTPS | `DataPathProbe.run` | 各 12/15 s | `1.0.0.1` 经 Direct、`1.1.1.1` 经当前线路、`www.apple.com` 测 DNS |
| └ 路由计数（后） | `routing-probe-snapshot` | — | |
| 判定 | `ConfiguredDataPathResult.isUsable` | — | 全部线路有出口 **且** 域名请求成功 **且** 路由计数只命中期望线路 |
| 地区判断 | 扩展 `performScenarioEvaluation` | 8 s | 连接后与自检**同时**进行；经 Direct 查 Apple 地区服务，失败再查 `1.1.1.1` |
| 首页自动场景 | `HomeView.refreshAutoScenario` | — | 请求扩展判断；切换场景后 `adoptSwitchedScenario` **再跑一轮自检** |
| 未通过后补测 | `DataPathRecheckPolicy` | 30 s / 120 s / 300 s | 只在前台；回到前台重置 |

诊断现状：App 日志只进 `os_log`；扩展只保留最后一个阶段；首页“详情”和“诊断信息”只有
一行摘要（版本、状态、对象计数、最近一次探测摘要、自动选场景、最近错误）。没有关联 ID
贯穿 App 与扩展，没有各阶段耗时，也没有历次连接记录。

## 2. 待验证的假设（不是结论）

1. **首页被自检阻塞**：系统已 connected，首页要等最多 90 s 的自检。这本身就会让“连接”显得很久。
2. **单一目标决定成败**：`1.0.0.1`、`1.1.1.1`、`checkip.amazonaws.com`、`www.apple.com` 都是境外站点，在国内直连时可能慢或不稳定；任一失败都会把整次判为“未通过”。
3. **线路试拨的两个目标共用一个期限**：第一个目标慢会吃掉第二个的时间。
4. **重复探测**：地区判断、首页自动场景、场景切换后的再次自检与首次自检同时触发，可能争用同一线路，并互相拖慢。
5. **后台/锁屏**：探测在 App 里，进后台就暂停；“有时有、有时无”可能与此有关。

每一条都要先用第 3 节的计时数据确认或否定，再决定改动。不能靠缩短超时来掩盖失败。

## 3. 第一阶段：可收集证据的版本（不改变连接行为）

目标是让下一次实机反馈直接带回能定位问题的数据。

- **连接会话时间线**（App Group 内有界 JSON，App 与扩展共写）：每次连接用现有
  `attempt_id` 作为关联 ID；事件包含墙钟毫秒时间、来源（app / tunnel）、阶段代码、耗时、
  结果码、取消原因和不超过 160 字的脱敏说明。最多保留最近 6 次会话、每次 120 个事件，
  文件总量不超过 256 KiB，超出后丢弃最旧的会话。
- **结构化探测结果**：每项检查记录目标、预期线路、耗时和结果码：
  `ok / timeout / dns / connect / tls / http / cancelled / not-run / inconclusive`。
  扩展的线路试拨、地区判断也写入同一条时间线。
- **取消与重试原因**：看门狗到期、进后台、断开、场景切换、补测排程与开始。
- **一键导出脱敏报告**：在现有“诊断信息”中加入版本与 build、系统版本、设备类型、
  当前状态、自动判断及依据、所选场景和被检测的线路名称、最近几次连接的完整时间线。
  默认不含密码、token、cookie、私钥、服务器地址、完整配置和浏览记录；线路只显示名称。
- 正常使用不增加网络请求；时间线写入在后台队列完成，失败不影响连接。

第一阶段实现与验收见 [验收记录](../verification/connection-diagnostics.md)。

## 4. 第二阶段：在基线数据上改行为（逐项对比）

只有第 3 节数据证实相应假设后才合入，并用同一组场景对比改动前后的耗时。

1. **最小连接成功条件**：系统 connected，且必要的就绪条件满足（启动包、TUN、引擎、
   AnyConnect 认证、Tailscale 登录）后，首页即显示“已连接”。自检转为后台健康检查，
   有独立的状态（检测中 / 通过 / 部分异常 / 未通过 / 未检测），不再阻塞首页。
2. **分线路判定**：Direct 与各条线路分别判定，每条用两个以上可在国内与境外到达的目标
   **并发竞速**，任一成功即该路径可用；只在全部目标都以网络错误失败时才判该线路失败。
   单个站点失败记为“测试站点异常/不确定”，不判整条线路坏。隧道启动成功不算访问成功。
3. **总预算与去重**：一次健康检查总预算固定（初定 25 s，以基线 P90 校准）；同一会话内
   的首次检查、补测、场景切换后检查合并为一个；新会话或网络切换使旧检查失效，旧结果
   不能覆盖新会话；断开、后台、锁屏立即取消，不留补测，不擅自重连。
4. **文案**：主屏分开展示“连接状态”和“自检状态”，二者各自准确。

## 5. 验收

- **共享核心 / 纯逻辑**：时间线存储的上限与轮转、结果分类、报告脱敏、补测策略，都用单元测试覆盖。
- **故障注入**：DNS 超时、站点不可达、慢握手、网络切换、恢复、旧检测被取消、主动断开。
  可在模拟器和单元测试中用注入的探测函数覆盖；隧道本身无法在模拟器运行，凡未在真机上跑
  过的部分都在验收记录中标明。
- **平台 UI**：iOS 构建加单元测试；首页文案与状态的对应关系另写测试。
- **耗时对比**：第二阶段每项改动都附上基线和改动后在同一场景下的 P50/P90。

## 6. macOS

macOS 连接已有 `ConnectionReport`（任务、事件、错误、回滚）。若 Mac mini 上也出现“连接很久”，
先用 Debug Server `/state` 中的 `connectionReport` 导出同样的时间线再判断，不套用移动端结论。

## 6.5 地区判断

所选场景是选择，不是检测到的地区。地区判断只有在查到地区码时才会选场景，查询失败时保留
原来的选择。诊断里要带出完整依据：地区码、查询路径、答复的服务、先前失败、耗时、网络标识、
多少秒前。网络变化后，旧的判断一律作废。核查结论与改动见[验收记录](../verification/connection-diagnostics.md)。

## 7. 实机验收清单（给 Dash）

每轮只需：

1. 冷启动 App → 连接 → 等到首页稳定 → 设置 → 诊断信息 → 分享（发回报告）。
2. 断开 → 再次连接 → 分享报告。
3. 已连接时在 Wi-Fi 与蜂窝之间切换一次 → 等 30 秒 → 分享报告。
4. 已连接时锁屏 1 分钟 → 解锁回到 App → 分享报告。
5. 若出现黄卡或连接很久：不需要别的操作，直接分享报告并注明大致时间。

6. 若锁屏或首页显示的场景和实际所在地不符（如显示“在国外”）：先回到 App 等 10 秒，
   再分享报告；报告里“自动选场景”那一行会写出这次判断用的服务、地区码和网络。

报告是纯文本，已脱敏；不需要另抓系统日志。
