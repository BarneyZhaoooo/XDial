# iOS 后台自动选场景与隧道内切换

2026-11-18 起草并实现。依据工作树 `878e455` 的代码、[DESIGN 8.1](../../DESIGN.md#81-场景自动选择)
与 [架构第 5 节](../../ARCHITECTURE.md) 整理。实现后的规则以 DESIGN 8.1 与架构为准，本文保留
起草时的现状、取舍与未验证项。**真机尚未验证：扩展内存峰值、扩展读 Wi-Fi 名称、后台网络变化
时的实际触发都要在真机上补证据（第 6 节）。**

## 1. 现状

- 自动选场景只在 App 前台运行（`ScenarioAutoPilot`），App 被挂起后不判断。
- 已连接时切场景由 App 先 `stopVPNTunnel`、最多等 15 秒、再用新场景 `startVPNTunnel`。
  期间系统 VPN 断开，流量要么直接走本地网络、要么失败，所有连接被打断。
- Go 核心已有 macOS 用的分阶段切换：候选 Box 在旁边启动、验收后 Commit、旧 Box 在
  Retire 后关闭，同一 AnyConnect / Tailscale 运行身份可借用不重拨。iOS 的启动不带运行身份，
  也没有使用这套接口。
- iOS 只有一个 packetFlow；Mac 版"每代各有回环入口、Provider 把新流量转给新一代"的做法
  不能直接照搬。

## 2. 结论

**已连接期间由 VPN 扩展独自判断和切换场景；切换不停系统 VPN。** 候选场景先在旁边完整
准备好（包括连上它需要的线路），只在提交那一刻把 TUN 从旧 Box 交给新 Box。准备或交接
失败时旧场景继续承载流量。不能并存准备时（两条不同的 AnyConnect，或两边都用到 Tailscale），
退回到"系统 VPN 不停、只换引擎"。没连接时 iOS 上没有我们的进程，仍由 App 在前台判断。

## 3. 设计

### 3.1 Go：TUN 交接（`core/libbox/tun_handover.go`）

- `SetSwitchTUNHandover(true)` 后，冷启动记下本代唯一的 TUN inbound；`PrepareSwitch*` 把
  候选配置里的 TUN inbound 摘下，候选 Box 不打开 TUN，因此准备与探测不影响用户流量。
- `CommitPreparedSwitch` 在原有验证之后关闭旧代 TUN inbound，再用同一份 fd 为候选代创建
  TUN inbound。候选打不开时把 TUN 还给旧代并返回可恢复错误；两边都打不开时返回
  `errTUNHandoverLost` 并经 `OnError` 报告，Provider 结束隧道交给既有重连。
- 交接需要 Box 运行期的服务注册表；交接模式下把 `box.New` 原本私建的注册表与 pause
  manager 预先放进本代上下文，运行期创建 inbound 与 `box.New` 内部完全一致。
- 旧 gVisor 栈终结的连接在交接时被重置；NE 会话、路由与 DNS 设置不变，没有流量漏到
  本地网络。保留旧连接需要包级分流，复杂度和内存都不值得，本版不做。

### 3.2 Go：运行身份（`GenerateNESession`）

与 `GenerateNEConfig` 同一份配置，另外返回本场景 AnyConnect / Tailscale 线路的运行身份。
iOS 每次启动都用带 AnyConnect 身份的入口，候选场景只有身份完全相同才借用已连上的会话。
Tailscale 仍放在各代 Box 里：iOS 配置带上所有启用的 Tailscale 线路，而由进程持有的 Tailscale
只支持一条；两代都含 Tailscale 时会争同一份状态目录，因此这类切换走换引擎。

### 3.3 场景目录（共享 Keychain）

- App 连接成功后，在后台为"可能被自动选中的场景"（登记了 Wi-Fi 的场景、地区表里的场景）
  和当前场景各生成一份启动包，连同判断规则存进共享 Keychain 的场景目录。启动包沿用
  按需启动的信封格式，参数里多带场景 ID 与运行身份。目录跟随运行中的 Profile 快照，
  Profile 改动在"应用改动"时重建。
- 判断规则：是否开启自动、各场景登记的 Wi-Fi、打包注入的地区表。用户手动选场景时 App
  先把目录里的自动关掉再切换，扩展不会改回去。

### 3.4 扩展：切换事务（`PacketTunnelProvider`）

- 同一时刻只有一个切换在进行，排在引擎串行队列上。
- 能并存准备（AnyConnect 身份相同或只有一边用到；Tailscale 只有一边用到）时：必要时先更新隧道远端
  地址 → `PrepareSwitchWithAnyConnectAndLineRuntimeIDs` → 经候选默认线路确认出口可达 →
  Commit（交接 TUN）→ Retire。
- 否则：先解析新 AnyConnect 服务器地址（此时旧引擎还在提供 DNS）→ 停旧引擎 → 在同一个
  NE 会话里起新引擎；新引擎失败时用旧启动包再起一次，仍失败就结束隧道。停旧引擎发出的
  "已断开"回调按引擎实例过滤，不会被当成掉线。
- 成功后更新按需启动信封（系统冷启动用新场景）、写出扩展状态并通知 App。

### 3.5 扩展：后台判断

- 触发：扩展自己的 NWPathMonitor 发现物理网络变化（接口或网关）并稳定 1.5 秒后；App 回到
  前台或打开「自动」时发消息请求判断一次。
- 线索与 App 相同：先读 Wi-Fi 名称（扩展也声明「访问 Wi-Fi 信息」），否则经 Direct 线路查
  出口地区。判断规则与 App 共用一份代码。
- 十分钟内刚从某场景自动切走、又在同一个网络里判断回该场景时不切，记为建议，App 前台时
  显示建议卡片。原规则不区分网络，离开办公室后十分钟内回来也不会切回；扩展记下切换时的
  网络特征（物理接口与网关），网络确实变了就照常切换。App 自己断开重连的旧路径保持原规则。
- Wi-Fi 名称只在扩展内存里用于判断，并随实时消息交给 App 显示；写进共享存储的状态去掉名称。

### 3.6 App

- 已连接时不再自己判断，只向扩展请求判断并显示扩展的结论；切换结果回到前台或收到扩展
  通知时同步到 Profile 与验收计划，并重新验收数据路径。
- 手动切换场景改为请求扩展在隧道内切换；扩展不认识这条命令（旧扩展）时退回原来的
  断开重连。

## 4. 不做 / 限制

- 切换瞬间已有连接会被重置（应用自行重连）。
- 没连接且没有开启「换网络后自动连回」时，后台不判断。
- tvOS 不变。

## 5. 风险

- 内存：切换瞬间扩展内同时有两代 Box（候选不带 gVisor TUN 栈），规则集在两代各加载一份；
  两边都用 Tailscale 时走换引擎，不会同时有两份 Tailscale。iOS 对 Packet Tunnel 扩展约 50 MB
  上限，未实测。
- 扩展读 Wi-Fi 名称依赖系统对 VPN 扩展的授权行为，未实测；读不到时只按出口地区判断。
